# 会话粘性：连续对话固定渠道与密钥

## 要解决的问题

多渠道、多上游密钥的网关默认每个请求独立做一次加权随机，于是同一段连续对话会在
权重接近的渠道之间、以及同一渠道的多把密钥之间来回跳。两个后果：

1. **上游视角异常**：同一条对话在多个账号之间跳，比正常使用更像异常流量，容易触发
   上游的风控与形态检测。
2. **费用失控**：首选渠道抖一下就被换到备用渠道，而备用渠道通常更贵；如果每请求
   重新随机，可能长期停在备用渠道上。

因此规则定为：**优先级、权重与密钥在第一次对话时确定，后续轮次沿用；只有渠道真的
坏了才切到备用；原渠道恢复后要切回原渠道。**

## 机制

### 1. 会话标识

同一段对话的识别顺序（`internal/logic/relay/conversation_affinity.go`）：

| 优先级 | 来源 | 说明 |
| --- | --- | --- |
| 1 | 客户端会话头 | `x-opencode-session` / `session_id` / `x-session-id` / `conversation_id` 等，与上游客户端身份用的是同一套头 |
| 2 | `metadata.user_id` | Claude Code 一类客户端在其中带 session 标识 |
| 3 | 首条用户消息指纹 | 前两者都没有时，用「同一段对话的首条用户消息不变」当锚点，兼容 chat `messages[]`、Responses `input[]`（字符串或消息数组）、Anthropic parts 数组 |

三者都取不到（例如只有 assistant 消息的续写请求）时**不做粘性**，保持每个请求独立
随机的原有行为——宁可少粘，也不把互不相关的请求错并成一段对话。

所有标识都会先做 SHA-256 再入 Redis 键，缓存键里不出现客户端原始会话串与提示词原文。

### 2. 渠道顺序粘性

第一次对话时把加权随机得到的候选顺序（去重后的渠道 ID 列表）写入 Redis；后续请求
按该顺序重排候选：

- 记忆里排在前面的渠道只要**出现在本次候选里**就一定排在前面；
- 坏掉的渠道（自动禁用、关闭时段、分组/白名单过滤、无可用密钥）根本不在候选里，
  于是自然落到下一跳——这就是「坏了切备用」；
- 它恢复后重新出现在候选里，靠记忆顺序自动回到第一位——这就是「恢复了切回去」，
  不需要额外的恢复探测逻辑。

只记「优先顺序」，不记「谁当前可用」：可用性每次请求实时重算，避免记忆里留下过期
状态。第一次对话之后新增的渠道排在这些渠道之后（优先级在第一次对话时就已定下）。

### 3. 密钥粘性

记忆键是 **(会话, 渠道, 模型)**（`internal/logic/channel/credential_affinity.go`），
同一渠道换了模型就要各自固定，避免模型间可用性差异互相踩。挑选规则：

| 记忆状态 | 本次行为 | 是否改写记忆 |
| --- | --- | --- |
| 无记忆（新对话） | 按加权随机挑一把 | 是 |
| 记忆里的密钥仍可用 | 直接用 | 否 |
| 记忆里的密钥被本次请求排除（刚失败过） | 本次临时换一把 | **否** |
| 记忆里的密钥已不在可用池（禁用/渠道级冷却/模型×密钥组合冷却/欠费/删除） | 换一把 | 是 |

「本次请求内的临时失败不覆盖记忆」是关键：否则一次抖动就能把整段对话永久换到另一把
账号上，正好造成用户想避免的来回跳。真正没费用（上游判欠费/失效并进入禁用或冷却）
才改写记忆，符合「一个密钥没费用了才换另一个」。

并发额度占满时同属「本次临时排除」，同样不改写记忆。

### 4. 与既有机制的关系

- **键级绑定**（`api_key_channel_credentials`）：语义是「这个 API Key 的所有对话共用
  一把密钥」，与「新对话随机一把」相反。因此带会话标识的请求不再走绑定表；不带会话
  标识的请求（管理端测试、单轮调用）保持原行为不变。
- **自动禁用与恢复**：渠道/密钥的禁用、冷却、恢复计划沿用原有实现，粘性只消费它们的
  结果，不新增状态机。
- **健康分加权**：仍在每个请求上生效，但只影响「第一次对话」那次排序与记忆失效后的
  重排，不会让已粘定的对话中途换走。

## 生效范围

- 只作用于对话转发入口（`internal/logic/relay/service.go` 的 `Handle`，覆盖
  `/chat/completions`、Responses、Anthropic 等对话端点）。
- 图片、音频、视频等非对话接口不参与粘性：它们没有「连续对话」语义。
- 关闭方式：客户端不带会话头、且请求体里没有用户消息时自动回到原行为。

## 缓存键与过期

| 键 | 内容 | TTL |
| --- | --- | --- |
| `aiferry:conversation-route:<apiKeyID>:<model>:<会话哈希>` | 渠道优先顺序 | 24 小时，命中续期 |
| `aiferry:conversation-credential:<会话哈希>:<channelID>:<modelID>` | 固定的上游密钥 ID | 24 小时，命中续期 |

命中续期保证连续对话进行期间记忆不会中途过期；对话结束后由 TTL 自然回收，不为短期
状态建表。

## 排障

- 日志 `会话密钥已切换 channel=… model=… credential=A→B（原密钥已不可用）`：只在
  记忆里的密钥真的不可用时出现。若频繁出现，说明该密钥在反复被禁用/冷却，应查上游
  连通性与余额，而不是粘性逻辑。
- 一次请求内出现多把密钥的尝试属于正常重试（本次请求失败才换），不代表粘性失效。
- 记忆读失败（Redis 异常）只退化为每请求随机，不阻断转发。

## 验证

本机单元测试覆盖：会话标识解析（会话头优先、`metadata.user_id`、首条消息指纹在多轮
中稳定、三种请求体形状）、候选重排（记忆优先、跳过不可用渠道、新增渠道追加、同渠道
多模型行不丢）、密钥挑选四类规则（新对话/复用/临时排除不改写/不可用改写）与 Redis
键的模型维度隔离。正式生效须以生产日志与请求回归确认，本机测试不等于生产验收。
